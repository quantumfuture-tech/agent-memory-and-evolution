# session-handoff

一个跨会话记忆协议：在下一次上下文归零之前，把“现在是什么状态、为什么这样、接手后怎么工作”写成一组可读的文件；下一次会话按固定顺序读回来。

它不保存聊天记录。它保存的是让下一个人能继续工作的状态。

## 它解决什么问题

会话结束时，模型的上下文被丢弃。下一次会话往往知道项目文件长什么样，却不知道：

- 上一次为什么停在这里，哪些方案已经试过并且失败；
- 哪个文件是当前状态，哪个只是历史；
- 接手后应该先做什么，什么不能碰；
- 这些信息里，哪些是用户明确说过的，哪些只是上一轮的猜测。

把整段对话重新贴回去通常不划算：对话里有大量重复、试探和已被推翻的中间结论。真正需要跨会话保留的是**状态、判断依据和接手约定**，不是逐字记录。

这个 skill 给出一套固定锚点和读取顺序，让“保存”和“读取”不再靠临场回忆。

## 为什么是“协议”，不是“格式”

格式只回答“内容怎么排”。协议还要回答下面这些问题：

| 问题 | 协议里的答案 |
|---|---|
| 保存到哪里 | 项目根的 `.handoff/`；每个记忆包一个子目录 |
| 哪些文件算状态 | 由记忆包自己的 `PROTOCOL.md` 声明资产表 |
| 接手先读什么 | `PROTOCOL.md` 固定的 `handoffReadList`，按声明顺序全文读 |
| 怎么判断文件有没有过期 | 状态画像文件末行的 `updated` 戳；读不到就一律当已变 |
| 谁有写权 | 接管记忆包 = 先整份读；同一时刻只该有一个持有者 |
| 冲突时听谁的 | 用户当前指示 > 元约定结构 > guidance 注入内容 |
| 什么不算状态 | 只存在于对话、未落盘的内容；需要用户确认后补写 |

同样的四个 Markdown 文件，换一套读取顺序和写回规则，就会得到完全不同的结果。协议约束的是这些关系，不是文件后缀。

## 5 分钟上手

### 1. 安装

把整个 `session-handoff/` 目录放进运行时的 skills 目录，例如：

```bash
cp -r session-handoff "$DSH_HOME/skills/"
```

这一步只是让 agent 能发现这份协议；真正的记忆数据放在**你的项目**里，不在 skill 目录里。

### 2. 建一个记忆包

在项目根建立 `.handoff/<记忆包名>/`。只有一个记忆包时，包名可以省略，直接使用 `.handoff/`。

最小形态是四份文件：

```bash
mkdir -p .handoff/blog-search
cp session-handoff/examples/PROTOCOL.md  .handoff/blog-search/
cp session-handoff/examples/STATUS.md    .handoff/blog-search/
cp session-handoff/examples/GUIDANCE.md  .handoff/blog-search/
cp session-handoff/examples/LOG.md       .handoff/blog-search/
```

示例是虚构的“给静态博客加搜索”，复制后先把 `PROTOCOL.md` 里的 `owner`、`task`、`记忆包Root` 和日期改成你的项目。

### 3. 写清三件事

- `PROTOCOL.md`：状态模型、接手必读清单、资产表、写规则。它只放结构和指针。
- `STATUS.md`：当前状态画像，最后一行带 `updated` 到秒的封条。
- `GUIDANCE.md`：接手后的行为约定（先汇报还是先动手、语气、禁区）。具体任务的行为放这里，不塞进协议结构。
- `LOG.md`：只追加的流水，记录发生过什么以及为什么。

### 4. 下次接手

在新会话里说“接手 blog-search”或“恢复”。agent 应按固定顺序：

1. 先看世界级两份文件（`REGISTRY.md`、`CHANNEL.md`；不存在则当场新建）；
2. 读记忆包的 `PROTOCOL.md`；
3. 检查状态画像末行的封条；
4. 按 `handoffReadList` 的顺序全文读取；
5. 建立资产索引，执行 `GUIDANCE.md` 里的接手流程；
6. 先复述理解，等用户确认后再动文件。

### 5. 收尾时存档

说“存档”或“保存”。agent 按协议更新状态、追加日志、盖版本戳，并逐文件回读确认。下一次会话就能从这些文件重建状态。

## 目录长什么样

```text
<项目根>/
└── .handoff/
    ├── REGISTRY.md              # 可选：这个世界有什么、归哪个记忆包
    ├── CHANNEL.md               # 可选：只追加的世界级流水
    └── blog-search/
        ├── PROTOCOL.md          # 读取约定：状态模型 + 必读清单 + 资产表 + 写规则
        ├── STATUS.md            # 状态画像；末行是带 updated 的封条
        ├── GUIDANCE.md          # 接手后的行为约定
        └── LOG.md               # 只追加的变更与决策流水
```

`REGISTRY.md` 和 `CHANNEL.md` 不属于任何记忆包，也不参与记忆包资产表校验。没有它们也能工作；协议选择在接手时补建，避免“缺一份文件就停下来”。

## 和“把对话存下来”的区别

| 把对话存下来 | 这套协议 |
|---|---|
| 保存逐字记录 | 保存状态、判断依据和接手约定 |
| 越长越完整 | 必读清单有长度预算，细节放索引后面 |
| 新会话从头读到尾 | 固定顺序：世界 → 协议 → 封条 → 必读 → 索引 |
| 谁都可以覆盖 | 资产表声明覆盖、追加或按需更新 |
| 过期与否靠感觉 | 状态画像末行有到秒的时间戳 |
| 行为靠临场发挥 | 接手后的行为写进 `GUIDANCE.md` |

对话记录仍然有用，但它是证据，不是状态。需要时再定点去翻。

## 已知限制

- **靠约定执行，不是运行时强制。** 协议规定读什么、按什么顺序读；没有沙箱阻止 agent 跳步或直接改文件。
- **不保证恢复对话原样。** 只存在于上下文、没有落盘的重要共识，需要用户在接手时补一句。
- **一个记忆包同一时刻只该有一个持有者。** 这是协作规则，不是锁；发现别处正在推进时，先问用户。
- **必读清单越长，接手越贵。** 需要控制条目数量，把可定点查询的内容放进索引，而不是全部设为 `full`。
- **封条只保证“可能变过”，不证明内容正确。** 状态文件仍可能与实际进展不一致，接手时应向用户核对。
- **世界级两份是可选且最终一致的。** 没有自动同步机制；漏记的条目只能在下一次接手时补。
- **没有加密和访问控制。** 记忆包按普通项目文件对待；敏感信息不应写进去。
- **协议本身没有自动化测试。** 它约束的是读取和写入流程，验证主要靠接手时的回读与用户确认。
