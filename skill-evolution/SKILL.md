# skill-evolution · agent 的发育引擎（元协议）

本 skill 是一份**元协议**：不携带任何具体技能内容，只提供 (a) 进化机制、(b) 固定锚点、
(c) 分发图、(d) 沿革与资格、(e) 作者培训的入口、(f) 护栏。具体技能由 `skills/` 目录承载，由本引擎按纪律产生与维护。

**两条道**：运行时是 `skills/<name>/SKILL.md` ＋ `references/` ＋ `scripts/`（一个包，随包分发）；
**沿革**（为什么是这样）住在另一个包 `.evolution/history/<name>/`。两者之间只有一条单向指针——技能自己不认识治理包。

## 0. 引擎的三条根认识（写死，不得漂移）

1. **机器在进步，不是因为你在进步。** 执行体每轮重建、不积累判断；能积累的只有这台电脑（skill、
   script、references、沿革、约定）。所以产出标准不是"写得好不好看"，而是**下一个失忆的执行体能不能据此做对**。
2. **摩擦是唯一的真实信号，而它只能来自机器外面。** 本引擎不会自己产生它——察觉不到"该有个 skill"
   是常态，正如察觉不到"漏了一页"。所以：绕远路、重复踩坑、被用户纠正、用户说"这儿有经验"——
   **这些症状本身就是调用本引擎的理由**，不需要更硬的触发条件。
3. **判断留在文本，确定压成程序。** 程序（`scripts/skillctl.js`）只做确定性操作与报告，永不自行决定
   晋升/淘汰；决定权在判断层（你和用户）。

## 1. 固定锚点

| 锚点 | 值 |
|---|---|
| 全局技能根 | `$DSH_HOME/skills/` |
| 项目技能根 | `<项目根>/.dsh/skills/` |
| 声明（唯一真源；投影化留 v16） | `$DSH_HOME/skills/.evolution/registry.yaml` |
| **沿革包（每技能一份）** | `$DSH_HOME/skills/.evolution/history/<name>/`：`entries/`（一条一文件）＋ `reads.jsonl`（谁领过）＋ `POINTER.md`（指向 `../../<name>/SKILL.md` 的单向指针） |
| **沿革条目** | `entries/<YYYYMMDD>-<id>-<正文哈希8位>.md`；字段见 §7；**文件名带正文哈希 ⇒ 改了正文就对不上名** |
| 读记录 | `history/<name>/reads.jsonl`（append-only：`at / by / session / package`）——资格门的事实依据 |
| 旧账（冻结，只读） | `$DSH_HOME/skills/.evolution/_legacy/`（v15 前的 friction.jsonl / proposals / 归档） |
| 归档区 | `$DSH_HOME/skills/.evolution/archive/<name>/`（**整个技能退役**才动；单条沿革只改 `state`） |
| 目录预览 | `$DSH_HOME/skills/.evolution/catalog.md`（投影，`skillctl render` 生成） |
| 本引擎 | `$DSH_HOME/skills/skill-evolution/`（`SKILL.md` ＋ `references/authoring.md` ＋ `scripts/skillctl.js`） |
| 格式版本戳 | **数据格式戳**见 `registry.yaml` 首行的 `conformsTo`（此处只写指针，不抄值）；**引擎版本**见本文页脚 |
| 技能包格式 | 目录 `<name>/SKILL.md`；frontmatter 必填 `name`(kebab-case)＋`description`；可选 `references/`、`scripts/` |

> `.evolution/` 在深度 2，不会被 skill 扫描器（深度 1）误认——这是**沿革不污染运行时**的物理保证：
> `history/` 只能住在 `.evolution/` 里，**不许进 `skills/<name>/`**；而确认门的落点不变：
> 只有移动到 `skills/<name>/` 才算活。

### 1.1 目录不是我们写的（源码核实，2026-10-30 复核）

harness（`dsh-tool-skill`）**每一步**从所有 modelInvocable skill 的 `description` 重建
`<available_skills>` 目录，超过 500 字符截断；条目摘要的 digest 一变就**重发一份完整目录替换旧的**，**不需要重启**。
目录行只有 `- name: description`——`whenToUse` 会被解析但不进目录。

由此四条纪律：

- **`description` 就是本引擎的脸**，也是整个系统的入口。它常驻、每轮计费、且只此一份。
- **不要手工维护目录**——没有这个文件，也不需要同步。改 `description` 就改目录。
- 改任何 `description` 视为**改常驻层**：需用户确认 + 升 version；**声明的作用半径 ≤ registry 授予的 tier 半径**（越界看谁授予，不看写多强）。
- **沿革不进 `skills/<name>/`**：它与运行时目录物理分离；单向指针只从治理指向运行时，反向没有指针。

## 2. 分发图（本引擎的第一性）

一条知识只有在**被读到**时才存在。所以问题不是"它多重要"，是"**它挂在哪张图的哪个节点上、谁在第几步读到它**"。

### 2.1 四个词

- **节点**：任何承载文本的位置——目录那一行、`SKILL.md`、`references/x.md`、`AGENTS.md`、沿革条目、store 的 `PROTOCOL`、用户这一轮的话。
- **边**：一段文本让读者去打开另一个节点。指针、指令、"先读 X 再动手"都算。**只要有文本，就能加边。**
- **根**：不需要任何动作就已经在上下文里的节点——技能目录行（每轮）、`$DSH_HOME/AGENTS.md`（每会话一次）、用户这一轮的话。
- **深度**：从根到某节点的最短跳数。**每多一跳，多一次"读不读"的赌注、多一次上下文成本。**

### 2.2 四条边规则

| 规则 | 内容 |
|---|---|
| **边带条件** | 写清"当……时，读它"。没有条件的边等于没有边——读者只能在所有分支间瞎试。 |
| **节点与路径无关** | 离开来路也能单独读懂；不许写"如前所述"。读者顺着条件进来，**条件就是来路**。 |
| **跨包单向** | 治理 → 运行时：可以。运行时 → 治理：不许。包是分发单位，包外的一搬家就断。 |
| **不许成环** | 环让"整份读"变成"读不完"。 |

### 2.3 树与图：树是默认，不是规范

包内默认成树（一个根、一支一个处境、好算成本、好推理），但**允许 DAG**：一个节点服务多个处境是合法的，
只要它自足、每条边各带条件。**"两个父亲 ⇒ 读者不知道从哪条路进来"是错的**（一次设计讨论里被推翻）——
读者就是顺着某个条件走进来的。共享节点省重复、少漂移；两处各抄一份才是双倍维护。

所以 `check` 不卡"单亲"，只卡结构上真会坏的四种：**目标存在、无孤儿、无环、深度 > 3 警告**。
"边写清条件没有""节点自不自足"判不了，归作者培训（§5），不归 `check`。

### 2.4 四类（图例）与六层（特例）

| 类 | 在图里是什么 | 代价 |
|---|---|---|
| **公告** | 根：目录那一行 | 按轮计费（必须极薄） |
| **领取** | 根 → 一跳：`SKILL.md` 全文 | 一次性一大块 |
| **机器** | 不在读路径上：`scripts/` 被执行 | 维护与可跑性 |
| **结构** | 开机注入的根：`AGENTS.md`、约定、harness | 改它就是改"我是什么" |

v12 的六层表是"图退化成一条路径"时的编号（公告=层4／领取=层2／机器=层3／结构=层6；层1是现场，层5是开机读的约定）。
它**不再是轴**，只作查表用。

### 2.5 判据与边界

**判据（每次诞生/迭代都要问）**：**这件事谁该看见、什么时候发、以什么代价进上下文？**
——问的是"挂在图的哪条边上"，不是"知识本身有多重要"。

**边界（必须同时写清，否则这段会变成口号）**：**事前闸门在本机只在一处可行**——脚本自己执行的动作（`skillctl`）。
写文件、改正文由执行体自己完成，**没有中间人**。能兑现的是：**没培训过的动作，事后一定能被查出来**。
**图说明"到得了"，读记录说明"走到了"——两样都要，缺一个就退化成口号。**

三条推论（v12 保留）：

- **一直往浅层堆东西会倒退。** 目录太长、加载太慢、我想不起来——**skill 本身会变成新的摩擦源**。
- **漏一次的代价可接受 → 领取；不可接受 → 公告或机器。** 漏一次的代价是返工，公告的代价是**每轮计费**——可逆性不同。
- **晋升需要判断，判断不外包。** `skillctl view` 只报告候选，不能自行下沉。

### 2.6 图之外：须知（orientation）

图只说明"到得了"，不说明"你为什么会在这里"。只有边，模型会机械地在节点间旅行——
被上一段文字带到下一段，不知道自己在受训。**须知**（`$DSH_HOME/AGENTS.md`，开机注入）给的是定位：
这是培训、不是岔路；这些材料有归属、有来历；你每轮失忆，而它们留给下一个你。

**分工**：图管可达，须知管定位。图让人找得到，须知让人知道**该不该来、来干什么**。
图做不到而须知能做到的三件事：① 把"读一份 reference"识别成上课，而不是检索答案（所以读全，不摘取）；
② 发现"该领的包不在"时主动去找，而不是就地发挥；③ 拒绝一条不该走的边。

**代价**：须知在根上（每会话注入一次），必须极短——三条以上就开始变成口号，而口号不会改变任何决定。

## 3. 生命周期：五个动作

### 3.1 记（note）

碰壁的当场：`skillctl note --what "事实" --lesson "那一眼" --scope <技能|无归属> --cause <5值> --type <枚举>`。
**三个字段必填**：scope（这堆归谁——决定谁有资格改）、cause（因谁而起——决定换读者时哪些要重估）、
type（哪类失灵——决定该不该下沉机器层）。**填不出来就先别记**：无法归因的账本是废的。

- scope：registry 里的技能名，或 `无归属`（允许粗糙，但必须带 cause 与 type）。
- cause：`task`（任务固有）／`user`（用户意志）／`agent-class`（凡 LLM 执行体）／`model`（本模型族易犯）／`harness`（平台）。
- type：**8 值封闭枚举 v1**——未经对账的断言／覆盖即销毁／本机工具约定／写完没回读／顺序做反／定位误判／验证工具本身没验／交付形态未适配读者。
  收口理由：v15 前 20 条账出现过 **19 个不同值**，自由文本让"复发"无法聚合。要加值 → 引擎修订（慢档），不许临场造词。
- 记录自动带会话指针（`cwd / session / seq / anchor`）；`--seq` 与 `--anchor` 至少给一个，否则事后无法回轨迹。

### 3.2 读（self / train）——资格

- **改一个技能之前**：`skillctl self <name>`——整份读入本体＋沿革，并在 `reads.jsonl` 写一行。
  没有这条记录，`merge` 会拒（§8.3）。
- **造/重写一个技能之前**：`skillctl train authoring`——领取 `references/authoring.md`（作者培训包）。
  没有这条记录，`add` 会拒。

### 3.3 提（propose / supersede）

`skillctl propose <name> --why "为什么" [--note "正文"] [--evidence f88,f91]`。
提案写进沿革包（`kind: 提案`, `state: open`），钉住**整包哈希 + registry 指纹 + version**。
一个技能同一时刻只许一条未结提案。正文不可变；要换方案就 `supersede` 旧的、再提新的。

### 3.4 批（merge / reject）

`skillctl merge <name> --why "理由"`。四道门，任一不过即拒（退出码 2）：
**① fresh**（整包哈希与 version 未变）；**② 读记录**（有匹配当前包哈希的 `self`）；
**③ check**（该技能范围内格式全绿）；**④ 批准者 ≠ 作者**。
通过后：version+1、registry 记 `packageHash: pending:<id>`、提案置 `merged`。
**顺序写死：propose → 批 → merge → apply → sync**。先改文件再 merge，等于把自己批准的东西变成 stale（`f107`）。

否决：`reject <name> --why`——**理由必须留下**，被否决的理由是最贵的负向知识。

### 3.5 扫（view / check）

- `skillctl view`：分布（cause × scope）、复发（repeatOf）、孤儿、未结提案、每技能的领取次数（**分母**——分得清"收敛的零摩擦"与"休眠的零摩擦"）。
- `skillctl check`：格式门。只报不改，退出码 2。卡的东西见 §9。

### 3.6 诞生（add）

`skillctl add <name>`（先 `train authoring`）→ 建 registry 条目（draft）＋ scaffold 骨架 →
写入正文（**渐进披露：正文是索引，references 按处境分岔**）→ 移入 `skills/<name>/` → `sync` → `check`。

## 4. 诞生阈值（什么值得结晶成 skill）

四条**同时满足**才晋升，外加一条铁律：

1. **跨任务可复用** —— 换一个项目/任务仍成立（不成立 → 项目特化，不进全局 registry）。
2. **有明确触发条件** —— 能写成一句「触发 + 能力」的 `description`。
3. **有可执行步骤** —— 能写成 procedure，或更高阶的 mechanism。
4. **踩过坑 / 有代价** —— 是真实摩擦逼出来的，不是凭空想出来的。

> **互补铁律**：必须编码「模型不会、但这里必须会」的本地知识。模型本来就会的（怎么写代码、怎么用 git）
> 不进 skill——否则只会稀释目录、拉低触发精度。

## 5. 作者培训包（不在本正文里）

要起草新技能、或重写某个技能的形态——**先读 `references/authoring.md`（岗位：作者）**。
它不随本技能加载：**读到这行，才知道它存在**；它是渐进披露的第三层，随包一起分发。

读完跑 `skillctl train authoring` 登记。没有这条记录，`add` 会拒——**上岗培训不是建议，是资格**。

### 5.C 事后评估：在一次 fork 里做（不是子 agent，是 fork 会话）

**为什么需要它**：主 agent 手里有最好的观察材料，但它的**上下文是最稀缺的资源**——
绝不能因为沉淀技能，就让"下一句关于工作的对话"里躺着一整套新 skill 的设计过程。

**机制：用户 fork 本会话**。fork **继承全部历史**——包括本引擎、registry、我读过的账本、以及**我的推理本身**。
它拿到的材料比任何"我写给子 agent 的 brief"都全，而它产生的上下文**长在它自己的会话里**，父会话一点不被污染。

**触发：由用户 fork，不由机制自动触发。** 摩擦够厚（某 scope ≥5 条）或有 `repeat` 时，
**agent 在会话收尾时主动报读数并问一句"够不够 fork"**——这个"提醒"由 agent 承担，因为没有别的钟会响。

**task 指令**：

0. **先回轨迹，再读自述。** 按条目的 `sessions[]` 逐个打开 `$DSH_HOME/sessions/<encoded-cwd>/<session-id>/session.v4.jsonl.zstd`：
   - 解多帧用 **`zstd -dc`**（skill: dsh-session-repair）；**不要用 node 的 zstdDecompressSync**——它只吃第一帧，会给你一行假日志。
   - 定位用 `python session_edit.py <plain.jsonl> --inspect` 的 turn／message 区间（skill: dsh-session-editor），再按 `seq` 取段。
   - **以轨迹为准**：`what` 与轨迹不符，批次记 `correctedFrom`，不得照抄自述。
   - **seq 会漂**：editor 会重排 seq。取不到该段时用 `anchor` 全文搜索重定位；仍找不到 → 该条标 `stale` + 理由，**不得静默跳过**。
   - 没有指针的旧条目：视为"只有自述"，评估必须写明这一限制。
1. 先读**被否决提案的 `why`**——不得重复提已被拒的方案。
2. 找**失败类型**，不是知识点：**它反复在"哪一类地方"看走眼？** 没看见（感知）、不知道（知识）、还是判断形状错？
3. 按 §2 的判据给**发放方式**的建议：感知类 → 机器或公告（公告最贵，要有理由）；知识类 → 领取；判断形状类 → 引擎修订（慢档）。
4. 允许**空手而归**："这批没有共同模式，不值得沉淀"是**合法结论**。

**产物分两档，绝不混送**：新技能/迭代/淘汰 → 有界可回滚，机器门 + 用户一句确认；
**引擎修订建议**（改规则/判据/schema）→ **自宪**，必须用户显式批，单独走 §10 慢档。

**硬约束**：skill 活在文件系统里——落盘就是交付，不需要"投递"回父会话；产出必须落盘；
**不得直接改任何 skill 文件**，只能提案；**批准者不得是提案作者**；评估完把条目置 `reviewed`（`skillctl review <id…>`）。

## 6. 执行端心智

- **碰一次壁，长一次眼**（主发动机）：撞墙本身不算账——**撞完说不出"事前该问哪一句"，才算缺了一个心眼**。
  产出两样：**事实**（原样）与**那一眼**（事前该问的那一句）。
  **重复和绕不是"又一个类型"，是连怎么错的都没学会**——标 `repeat`，优先。
  **别自己扛**：升级交给一次 fork（§5.C）——机器会自己收下改动。
- **会话收尾报一次读数**：`skillctl view`，主动问用户"够不够 fork"。
- **分层意识**：内容层（产 skill 本体）、元层（改本引擎/schema，需确认）、支线层（临时探索，就地完成，不入库）。
- **对话权威 > 文件权威**：用户当前指示优先于 registry 任何记录。
- **覆盖不丢信息**：refine 前确认被替换内容里没有未沉淀的关键信息；`openIssues` 悬空必保留到真解决。
- **复用而不重建**：新建前先查 registry；能 refine/merge 就不新建。
- **不表演 / 不追指标**：不为"看起来有产出"写 skill；判据只有一条——**下一个失忆的执行体是否更容易做对**。
- **不用装置替代指令**：一句话能解决的问题，不要为它造检测机制。
- **加判据 / 造装置之前**（`f11`）：会不会误伤"解释它自己的文字"？先拿一段解释性文字当反例跑一遍。
- **断言一个缺口"必须立刻修"之前**（`f2`）：这是**我确认过**的事实，还是**我想让它成立**？分不开就先说"我不确定"。
- **写完先回读**（`f13`／`f16`）：① 改完 .js → 先 `node --check` 再执行；② 改追加型文件 → 回读末两行，确认旧内容还在。

## 7. 沿革条目：一种形态，一个状态机

字段：`id / at / kind / scope / cause[] / type / state / why / evidence[] / by / sessions[] / pin / legacy?`

- **kind**：`观察`（撞过的壁 ＋ 那一眼）或 `提案`（要改什么、为什么）。
- **state**：观察 `open → reviewed`；提案 `open → merged | rejected | superseded`；通用 `archived`。
- **正文不可变**：文件名带正文哈希（`…-<sha8>.md`），`check` 重算；要改就新开一条、旧的置 `superseded`。
- **永不删**：只追加、只改状态。历史没有回滚面——git 只保护"提交过的中间态"，而被否决那一刻最没人提交。
- **证据**：`evidence` 指向它处理了哪些观察（多对多、有向）。提案必须带 `why`；否决同样必须带 `why`。

## 8. 三条承重规则（理由优先：理由才可被重新演绎）

### 8.1 提案钉在它所提议的那个状态上（整包哈希）

**做法**：`propose` 记下**整包哈希**（技能目录内所有文件按路径排序）＋ registry 指纹 ＋ version；`merge` 前重算，不一致即 stale，**拒绝收编**。

**理由**：执行的人每轮被换掉，**这台电脑是唯一的记忆**。提案与目标一旦脱钩，人批准的就是一个**已经不存在**的 diff。
**所以**：凡提案必绑定；绑不上就不许批。钉整包而不是单文件——因为 `references/` 也是本体的一部分。

### 8.2 来源是声明的，不是推断的（`write` 是硬约束）

`write` 只有三个值：`user`（人写的，agent 只能 `propose`）、`agent`（agent 自己写的，可自行 refine）、`user-gated`（待定）。
**理由**：执行的人每轮被换掉，所以"这一块是谁写的"是这台机器**唯一**能区分人与自己的东西的方式。
若交给推断，人的作品会被静默改写，**而且没有任何人会记得它原本长什么样**。
**所以**：来源一旦不确定，就不许自动改。

### 8.3 上岗纪律（资格门）

**做法**：改技能前 `self <name>` 留读记录，`merge` 前校验；造技能前 `train authoring`，`add` 前校验。
没领过的人**只能读、只能提**。

**理由**：前两条管"钉在哪个状态上"与"谁写的"，但都假设改的人已经知道**为什么是这样**。
沿革里躺着的正是这件事——被否决的方案、试过没用的写法、上一次为什么这么定。
不读就改，等于把过去所有的试错重做一遍，而且重做时还自以为在创新。
"读过"不靠自觉，靠**一行可对账的记录**——它与哈希绑定同源：机器是唯一记忆，所以"我知道"必须落成"盘上有"。

**元规则在哪里**：写在 `$DSH_HOME/AGENTS.md`（开机注入、跨工作区）——
**会改变持久资产的动作（改技能、改 store/约定、对外发布、动别人的包），先领对应的包**。
本节是它的机器形态；`AGENTS.md` 是它的公告形态。日常读写不在此列——范围只到"会改持久资产"。

## 9. registry 与 skillctl

**registry 是生命周期的声明**（**本轮不动**——设计待定 4 计划投影化，留给 v16）；**沿革包是观察与提案的真源**；
`name`/`description` 以各自 `SKILL.md` 的 frontmatter 为准。三者由 `check` 强制对齐。

**五个动作 ↔ 命令**（旧名保留为别名；硬切命令名留给下一版）：

| 动作 | 命令 | 旧名 |
|---|---|---|
| 记 | `note` | `friction add` |
| 读 | `self <name>` ／ `train authoring` | —（新增） |
| 提 | `propose` ／ `supersede` | `propose` |
| 批 | `merge` ／ `reject` | `accept` ／ `reject` |
| 扫 | `view` ／ `check` | `report` ／ `lint` |

**check 必须挡住这些漂移**（格式门卡在 `merge` 路径上，不是只报告）：
① registry 有条目但磁盘无 SKILL.md；② 磁盘有 skill 但 registry 无条目；③ name ≠ 目录名或非 kebab-case；
④ `description` 为空或超长（>500）；⑤ `lineage` 指向不存在的条目；⑥ tier/status/enforces/write 越界；
⑦ 条目顶层野字段（v15 起不再校验 `proposals`）；⑧ **未结提案已 stale**；⑨ 被否决的提案缺 `why`；
⑩ **沿革条目 schema 越界**（kind/state/cause/type/scope/by）；⑪ **文件名哈希与正文不符**（正文被改过）；
⑫ **evidence 指向不存在的条目**；⑬ **指针指向不存在的文件**；⑭ **孤儿引用**（没人指到）；⑮ **引用成环**；
⑯ **包哈希漂移**（改了本体/references/scripts 却没 `sync`）。

**registry 一律经 `skillctl` 写入，不手改 YAML**（唯一例外：用户直接编辑，之后必须 `check`）。
理由：唯一真源一旦有两个写入口，就不再是唯一。

**本机事实（`f9`，2026-09-30 核对）**：`node -e` 在本机 PowerShell 里会被**吞掉反引号**——
**一律写 .js 文件再 `node <文件>` 跑**，别内联。

**写"实测／核实"结论时的硬要求（`f15`）**：凡"实测／核实／已验证"这类断言，**必须带 (YYYY-MM-DD 核对) ＋ 出处**。
理由：不是事实过期，而是**写的时候没标它什么时候为真**——没有时效的"实测"会被下一个执行体当成无条件事实。

## 10. 护栏与优先级

- **优先级**：用户权限 > registry schema > skill 内容。冲突时停下问用户。
- **防漂移**：本引擎自身、registry schema、任何 meta 层 skill、以及所有 `description` 的改动，**必须用户确认 + 升版本**。
- **确认门**：所有诞生/迭代/合并/淘汰，一律 提案 → 用户 approve/edit/reject。**人永远是主编，agent 是起草人。**
- **自述 vs 自宪**：skill、registry、状态文件是自述（快档）；harness 代码与约定是自宪（慢档）。
- **版本耦合**：受管 skill 与 registry 都盖 `conformsTo` 戳；**本正文不抄具体版本号**——看 `registry.yaml` 首行与 `check` 输出。
- **资格门不可绕过**：`merge` 前必须有匹配当前哈希的读记录；没有就是没读过，不许改。
- **顺序即判据**：propose → 批 → merge → apply → sync（`f107`）。

## 11. 与 session-handoff 的分工（对偶红线）

| | session-handoff | skill-evolution |
|---|---|---|
| 尺度 | 工作区（一个房间） | 整台电脑（整个生命） |
| 存续什么 | 局域自我（这单的经验/记忆/唤醒） | 全局躯体（跨任务的肢体） |
| 产物 | `.handoff/` 状态文件 | 全局/meta skills + 沿革包 + registry |
| 生命周期 | 快照式 save/load | 进化式 记→读→提→批→扫 |
| 速度 | 每次会话 | 每次摩擦 |

**红线**：本引擎**不记「某项目到哪了」**（那是 `.handoff` 的事）；只记「这类事怎么做、这个能力该不该有」。

**同构**：store 的 `PROTOCOL → 必读清单 → 资产` 与技能包的 `SKILL.md → references` 是同一张分发图的两个实例；
上 store 与 `self` 是同一条边（整份读＝写权对价）。

## 12. 边界（不做什么）

- 不复读模型已知的知识（互补铁律）。
- 不承载任何具体技能内容（那是各 SKILL.md 的事）。
- 不维护项目状态（那是 session-handoff / `.handoff` 的事）。
- 不存长文教训（那是经验资产的事）。
- 不手工维护 skill 目录（harness 自动渲染）。
- 不自行晋升/淘汰（`view` 只报告）。
- 不在未确认前把提案变成活 skill（确认门）。
- **不绕过哈希绑定收编过期提案**（§8.1）。
- **不直接改 `write: user` 的条目**（§8.2）。
- **不绕过资格门**（§8.3）：没读过沿革，就只能读、只能提。
- **不为"一句话指令就能解决"的问题造检测装置**。
- **不让元工作的设计过程留在主 agent 的上下文里**（§5.C）。
