# skill-evolution · agent 的发育引擎（元协议）

本 skill 是一份**元协议**：不携带任何具体技能内容，只提供 (a) 进化机制（四算法）、(b) 固定锚点、
(c) 深度判定、(d) 作者教学、(e) 护栏。具体技能由 `skills/` 目录承载，由本引擎按纪律产生与维护。

## 0. 引擎的三条根认识（写死，不得漂移）

1. **机器在进步，不是因为你在进步。** 执行体每轮重建、不积累判断；能积累的只有这台电脑（skill、
   脚本、registry、约定）。所以产出标准不是"写得好不好看"，而是**下一个失忆的执行体能不能据此做对**。
2. **摩擦是唯一的真实信号，而它只能来自机器外面。** 本引擎不会自己产生它——察觉不到"该有个 skill"
   是常态，正如察觉不到"漏了一页"。所以：绕远路、重复踩坑、被用户纠正、用户说"这儿有经验"——
   **这些症状本身就是调用本引擎的理由**，不需要更硬的触发条件。
3. **判断留在文本，确定压成程序。** 程序（`scripts/skillctl`）只做确定性操作与报告，永不自行决定
   晋升/淘汰；决定权在判断层（你和用户）。

## 1. 固定锚点

| 锚点 | 值 |
|---|---|
| 全局技能根 | `$DSH_HOME/skills/` |
| 项目技能根 | `<项目根>/.dsh/skills/` |
| 治理层（**唯一真源**） | `$DSH_HOME/skills/.evolution/registry.yaml` |
| staging（提案草稿区） | `$DSH_HOME/skills/.evolution/proposals/<name>.md` |
| 摩擦力账本 | `$DSH_HOME/skills/.evolution/friction.jsonl`（**append-only**：事实 + 那一眼；已评估的移入 `friction-reviewed.md`） |
| 归档区 | `$DSH_HOME/skills/.evolution/archive/<name>/` |
| 目录预览 | `$DSH_HOME/skills/.evolution/catalog.md`（`skillctl render` 生成，供人审阅） |
| 本引擎 | `$DSH_HOME/skills/skill-evolution/`（`SKILL.md` + `scripts/skillctl.js`） |
| 格式版本戳 | **数据格式戳**见 `registry.yaml` 首行的 `conformsTo`（**此处只写指针，不抄值**）；**引擎版本**见本文页脚。**两者故意分开**——读到不认识的戳时，才判断得出"该升级程序"还是"该拒绝读"。<br>★【2026-10-13 修】这一格原先抄着 `conformsTo: skill-evo-v2` —— **抄了，而且过期了**（实际 `v3`），**与同一格的括号、§10、以及第 395 行三处自相矛盾**。讽刺的是那个括号里讲的正是"抄了就会过期"这条教训（`f19`），而写下它的同一格仍在犯 ✗ 按本引擎自己的规矩：**会过期的值不进正文，只写指针**。 |
| skill 格式 | 目录 `<name>/SKILL.md`；frontmatter 必填 `name`(kebab-case)+`description`，可选 `whenToUse`/`metadata` |

> staging 与 registry 都在 `.evolution/`（深度 2），不会被 skill 扫描器（深度 1）误认，因此
> **提案落进 staging 不等于生效**——这就是"半自动"确认门的物理落点：只有移动到 `skills/<name>/` 才算活。

### 1.1 目录不是我们写的（源码核实）

harness（`dsh-tool-skill`）**每一步**从所有 modelInvocable skill 的 `description` 重建
`<available_skills>` 目录，超过 500 字符截断；条目摘要（name+description）的 digest 一变就**重发一份
完整目录替换旧的**，**不需要重启**。

由此三条纪律：

- **`description` 就是本引擎的脸**，也是整个系统的入口。它常驻、每轮计费、且只此一份。
- **不要手工维护目录**——没有这个文件，也不需要同步。改 `description` 就改目录。
- 改任何 `description` 视为**改常驻层**：需用户确认 + 在 registry 里升 version。

## 2. 入上下文机制（本引擎的判断核心）

同一份知识，可以停在不同的**发放方式**上。**发放错了 = 该在的时候它不在上下文里。**

六层不是"埋得多深"，是**谁发、什么时候发、以什么代价进上下文**：

| 层 | 谁发 | 什么时候进上下文 | 现在必然进吗 | 谁强制 |
|---|---|---|---|---|
| 1 | 当前上下文 | 你 | 立刻 | — | 无 |
| 2 | skill 正文 | 你（领取） | 上岗时全量领 | 否（靠目录 + 我主动加载） | 解释 |
| 3 | skill 自带脚本 | 机器 | 不必进——机器替你做对 | 否（随 skill 加载） | 机器 |
| 4 | `description`（常驻公告） | 系统 | **每轮都进**（所以必须极薄） | **是** | 解释 |
| 5 | 约定 / registry | 你（开机读） | 下次开机 | 否（需主动读） | 解释 + 人的确认门 |
| 6 | harness 代码 / 沙箱 | 机器 | 重启级 | 是（结构性） | 机器 |

**判据（每一次诞生/迭代都要问）**：

> **这件事谁该看见、什么时候发、以什么代价进上下文？**
> ——问的是"发放方式"，不是"知识本身有多重要"。

**必须同时写清一条边界（否则这段会变成口号）**：**事前闸门在本机做不到**——写文件、改正文由**执行体自己**完成，
**没有中间人**（六层里真正有闸门的只有第 3 层：脚本自己是执行者，能在动手前要求前置条件）。
能兑现的是：**没培训过的动作，事后一定能被查出来**。这仍是从无到有，但**不是同一句话**。

三条推论：

- **一直往浅层堆东西会倒退。** 目录太长、加载太慢、我想不起来——**skill 本身会变成新的摩擦源**。
  所以"条目数"不是成绩；**发现（找得到）比内容更重要。**
- **漏一次的代价可接受 → skill；不可接受 → 常驻层或强制层。** 这是选层的真正依据，不是"重不重要"。
  理由：漏一次的代价是**本可避免的返工**，而第 4 层（常驻）的代价是**每轮计费**——
  两种代价的可逆性不同，**所以只在有理由时才动第 4 层**。
- **晋升需要判断，判断不外包。** `skillctl report` 只报告候选，不能自行下沉。

## 3. 生命周期四算法（硬编码，固定顺序，不得自由反推）

### 3.1 诞生（birth）
1. 识别摩擦点（过 §4 阈值）。
2. 读 `registry.yaml`，查是否已有 skill 覆盖此摩擦（**复用而不重建**）。查法：`skillctl list`。
3. 按 §5 作者教学起草完整 `SKILL.md` + 一句话提案（补什么缺口、血缘 `bornFrom`、**停在哪一层**）。
4. 落 staging：`proposals/<name>.md`。
5. 向用户提议（diff + 理由 + 选层理由），等 approve / edit / reject。
6. approve → `skillctl add <name>` 建骨架 → 写入正文 → 移入 `skills/<name>/` → registry 登记
   （`status: active, version: 1` + provenance + changelog），跑 `skillctl lint`。

### 3.2 迭代（refine）
1. 使用中发现某 skill「不够用 / 有错 / 过时」→ 先 `skillctl set <name> skips+1` 与 `openIssues` 记录。
2. 起草修订：`SKILL.md` diff + changelog 条目（version+1）。**若问题是"它该被想起来却没人想起"，
   改的是 `description`，不是正文。**
3. 向用户提议 diff，等确认。
4. approve → 应用 + registry `version+1` + changelog 追加（不删旧条）+ `lint`。

### 3.3 合并（merge）
1. 发现两个 skill 职责重叠 → `skillctl report` 也会提示。
2. 起草合并方案：谁吸收谁、正文如何并、被吸收者 `lineage.supersededBy`。
3. 提议，等确认。
4. approve → 应用 + 被吸收者 `status: superseded` + 吸收者 `lineage.supersedes` 记录。

### 3.4 淘汰（retire）
1. 触发（§7）：长期 0 hit / 被取代 / 明确过时。
2. 起草归档提议（理由 + 去向）。
3. 提议，等确认。
4. approve → `status: archived` + `lineage` 记录；skill 目录移入 `archive/<name>/`。

## 4. 诞生阈值（什么值得结晶成 skill）

四条**同时满足**才晋升，外加一条铁律：

1. **跨任务可复用** —— 换一个项目/任务仍成立（不成立 → 项目特化，不进全局 registry）。
2. **有明确触发条件** —— 能写成一句「触发 + 能力」的 `description`/`whenToUse`。
3. **有可执行步骤** —— 能写成 procedure，或更高阶的 mechanism。
4. **踩过坑 / 有代价** —— 是真实摩擦逼出来的，不是凭空想出来的。

> **互补铁律**：必须编码「模型不会、但这里必须会」的本地知识。模型本来就会的（怎么写代码、怎么用 git）
> 不进 skill——否则只会稀释目录、拉低触发精度。

## 5. 作者教学段：把「一次摩擦」抽象成一个 skill（全引擎最难、最核心）

先判层级，再走对应起草法：

- **Level 1（能力/流程类）**：摩擦是「某类任务怎么做」→ 走 5.A。
- **Level 2（机制/元协议类，即自我存续器官）**：摩擦是「agent 自身怎么跨会话存在」→ 走 5.B。

### 5.A 起草 Level 1（能力/流程）
1. **判定**：一次性 vs 一类（过 §4 四条件 + 互补铁律）。
2. **抽象**：找「这类事怎么应对」的稳定步骤，不写「这次怎么解」的病历。
3. **触发器**：一句话「当……时，用本 skill 做……」写进 `description`/`whenToUse`。
   **这句话要和用户会说的原话、以及你会感觉到的症状对齐**——否则触发不了，等于不存在。
4. **步骤/清单/排错**：把可执行内容写成 procedure + checklist + 排错速查。
5. **可脚本化则脚本化**（§2 的第 3 层：**机器发放**——它不必进上下文，因为它替你把事做对）：
   重复劳动若能固化，写进 `scripts/`
   （如 wechat-messages 的 `wxdb.js`、本引擎的 `skillctl.js`）——脚本背书的 skill 杠杆远高于纯 prose。
   **代价要一起算**：脚本要维护、要能被下一个人跑起来；只值一次的事别固化成脚本。
6. **自解释**：正文第一段让陌生模型立刻知道「这是什么、何时用、怎么用」。

### 5.B 起草 Level 2（机制/元协议，自我存续器官）
在 5.A 之上追加（同一套通用抽象方法推进到更难的 meta 类问题，不是独立配方）。
目标产物 = 一个「让 agent 跨会话继续存在的机制」，**质量标杆 = `session-handoff`**
（元层面适配各类工作接续，泛化 + 特化结合）。本引擎自身就是同一标准的产物，可当范例读。

**必含的不变式清单**（逐项自问，缺一即返工）：
1. **元协议声明**：本 skill 不承载具体内容，只承载机制 + 教学。
2. **固定锚点**：存储根、协议文件位置、格式版本戳（`conformsTo`）写死。
3. **硬编码算法**：核心流程固定顺序、不得自由反推。
4. **结构 vs 行为分离**：结构文件只放指针 + schema，行为归专用文件（如 guidance）。
5. **教学厚度**：教执行端「心智」，教撰写端「哪些维度可控」的菜单（只喊"内容自定义" = 无效教学）。
6. **优先级护栏**：用户权限 > 固定结构 > 注入内容；冲突停问。
7. **版本耦合 + 防漂移**：运行态盖戳；约定改动须用户确认 + 升版本。
8. **自解释**：每个资产首行自述 + 正文首段冷启动可重建。
9. **覆盖不丢信息 / 对话权威 > 文件权威 / 复用而不重建**。
10. **边界**：明确「恢复什么、不恢复什么」。
11. **入口自查**：它的 `description` 是否让人（和下一个你）在该想起来的时候想得起来？
    这是 meta 类 skill 最容易死的地方——**机制再漂亮，叫不醒也等于没有。**

### 5.C 事后评估：**在一次 fork 里做**（不是子 agent，是 fork 会话）

**为什么需要它**：主 agent 手里有最好的观察材料（工具调用记录、失败原文、自己思考里的磕绊），
但它的**上下文是最稀缺的资源**。绝不能因为沉淀技能，就让"下一句关于工作的对话"里
躺着一整套新 skill 的设计过程。

**机制：用户 fork 本会话**（不是开子 agent）。
fork **继承全部历史**——包括本引擎、registry、我在对话里读过的账本、以及**我的推理本身**。
所以它拿到的材料**比任何"我写给子 agent 的 brief"都全**，而它产生的"怎么升级"那一大堆上下文
**长在它自己的会话里，父会话一点不被污染**。

| | 主 agent（当前工作） | fork 会话（润滑 + 自改造） |
|---|---|---|
| 产出 | 活 + **一条摩擦记录**（事实 + 那一眼） | 分类、找模式、出提案 |
| 上下文 | 读得出，**不可写回** | 拿得到全量过程材料（含推理） |

**触发：由用户 fork，不由机制自动触发。**
摩擦账本够厚（≥5 条）或有 `repeat` 时，**agent 在会话收尾时主动报读数并问一句"够不够 fork"**——
这个"提醒"由 agent 承担，因为没有别的钟会响。

**一条实测事实（2026-09-30 更正）**：**fork 继承全部历史；而子会话的上下文里现在有身份标记**——
本机 harness 的插件 `@deepseek-ai/dsh-system-prompt` 会注入 `subagent:delegation`
（"You are a delegated subagent…"）**并给出 parent agent id**（从 `subagent_fork` 出来的子会话日志逐帧解压核对：74 帧全成功）。
原话"**子会话的上下文里一个字都没有**（系统提示、运行时快照、目录里都没有 fork 标记）"**已证伪**——
那是 2026-09-29 的实测，**harness 之后变了**。（留档理由：假事实比没有事实更坏，它会被下一个执行体当依据。）

> **别"推断"身份；但"念出来"的身份要用。**
> 实测：**即使标记就在上下文里**，那个子会话的第一轮推理**仍先自称"我是 parent"**（`Wait — I am the parent…`），
> 要靠这条注入才纠正——**继承全部历史 ⇒ 默认把父的身份也继承了**。
> 所以：**别把机制建在身份上**（身份会被叙事盖住），也**别否认已经念出来的事实**（声明 > 推断，同 §8.2）。
> 更省的做法仍然是：把这类工作**当成一条支线**——
> **支线自己的 `<store>/GUIDANCE.md`**（接手后行为：先跑哪几条自检、期望值、汇报风格、禁区）
> + **支线自己的 store**（住在自己的工作区里，**不写进主线 store**）。
> 用户在工作区根说一句"接手 XX"，新会话就能自己接上，**不需要任何会话知道"我是不是 fork"**。
> 参照实例：家教工作区的 `jiajiao-kanban`（§0.5）→ **支线自己的 store** `.handoff/jiajiao-kanban/`
> （2026-09-30 起；此前是把状态硬编码在项目文档 `接单看板/交接.md`，现已拆为 store + 指针 + 稳定知识）。
> **别为此在主线账本加结构字段**（`role: fork-state`、`task:` 标注、`handoffReadList` 分组）——
> 2026-09-29 实测证伪：加了也不用。

**task 指令**：
1. 先读**被否决提案的 `why`**——不得重复提已被拒的方案。
2. 找**失败类型**，不是知识点：**它反复在"哪一类地方"看走眼？** 逐条问：这是"没看见"（感知）、
   "不知道"（知识）、还是"判断形状错"？
3. 按 §2 的判据给出**发放方式**的建议——问"**这件事谁该看见、什么时候发、以什么代价进上下文**"：
   感知类失败（没看见）→ 机器发放（脚本）或常驻（第 4 层，**代价最贵、要有理由**）；
   知识类 → skill 正文（上岗时领取）够用；判断形状类 → **属于引擎修订，走慢档**。
4. 允许**空手而归**："这批没有共同模式，不值得沉淀"是**合法结论**。

**产物分两档，绝不混送**：

| 产物 | 半径 | 门 |
|---|---|---|
| 新技能 / 迭代 / 淘汰 | 有界、可回滚 | 机器门（lint + 哈希绑定）+ 用户一句确认 |
| **引擎修订建议**（改规则/判据/schema） | **自宪** | **必须用户显式批**，单独走 §10 慢档 |

**硬约束**：
- **skill 活在文件系统里，不活在对话里。** 落到文件**就是**交付——harness 会自动失效缓存并重发目录，
  主会话与后续所有会话自然用上新版本。**不需要把升级"投递"回父会话**；总结报告是礼节，不是媒介。
- **产出必须落盘**：**fork 会话的推理不回流**，不落盘就随它那次会话死掉（而它不会被再 fork）。
- **不得直接改任何 skill 文件**，只能提案（**一个自动写者是最危险的形状**）。
- **批准者不得是提案作者**（依据：LLM 自评准确率仅 46.4%，"同一个 AI 不得既编辑又打分"）。
- 评估完调 `skillctl friction clear`（移入 `friction-reviewed.md` 归档，append-only 不丢）。

## 6. 执行端心智

- **碰一次壁，长一次眼**（本引擎的主发动机）：
  撞墙本身不算账——**撞完说不出"事前该问哪一句"，才算缺了一个心眼**。
  所以每次碰壁，你要产出两样东西：**事实**（原样，不解释）与**那一眼**（事前该问的那一句）。
  记法只有一条命令：`skillctl friction add --what "事实" --lesson "那一眼" [--type "失败类型"]`。
  **`--type` 要声明**（同类型的待评估条目自动判 `repeat`）——本账本有过一次"7 条同族、`repeat` 全漏"的教训：
  类型**是声明的，不是工具猜的**（§8.2）；漏了类型，下一个 fork 会把同一批重做一遍。
  **重复和绕不是"又一个类型"，是连怎么错的都没学会**——它证明上次没修好，标 `repeat`，优先。
  **别自己扛**：升级的事交给**一次 fork**（见 §5.C），不急——机器会自己收下改动。
- **会话收尾时报一次读数**：`friction list`，然后**主动问用户"够不够 fork"**。
  这是 agent 的职责，因为没有别的钟会响（见 §5.C）。
- **分层意识**：时刻清楚自己在哪一层——主线内容层（产 skill 本体）、元层（改本引擎/registry schema，
  需用户确认）、支线层（临时探索，就地完成，不入库）。
- **对话权威 > 文件权威**：用户当前指示优先于 registry 任何记录。
- **覆盖不丢信息**：refine 覆盖前，确认被替换内容里没有未沉淀的关键信息；`openIssues` 悬空必保留到真解决。
- **复用而不重建**：新建前先查 registry；能 refine/merge 就不新建。
- **自解释**：每次写出的 skill 都要通过 §5.A(6) / §5.B(8) 的自解释自检。
- **不表演**：不为"看起来有产出"而写 skill。**这台电脑跨会话可对账**——你吹的牛下个月还在，
  而且会被下一个你读到。诚实在这里不是美德，是唯一能过时间检验的策略。
- **不追指标**：不追求"条目数""对齐轮数"下降这类指标。它们能被伪装（最省事的优化是更早地附和）。
  真正的判据只有一条：**下一个失忆的执行体，是否更容易做对。**
- **不用装置替代指令**：一个"给一句话就能解决"的问题，不要为它造检测机制。**造装置看起来像进展，
  但它通常是在替换更简单的东西。**（这条本身来自一次 `repeat` 摩擦力记录。）
- **加判据 / 造装置之前**（`f11`）：① 它会不会误伤"**解释它自己的文字**"？② **先拿一段解释性文字当反例跑一遍**。
  实例：一条"事实类文件里不许出现提交号"的自检，先把**解释这条自检的那句话**判成了违规——判据的假阳性
  同样消耗信任，而信任一旦没了，判据就会被绕过。
- **断言一个缺口"必须立刻修"之前**（`f2`，已被按回三次）：这是**我确认过**的事实，还是**我想让它成立**？
  分不开时，先说"我不确定"，别先动手——**未经对账的断言，是这批摩擦里唯一的复发性失败类型**。
- **写完先回读**（`f13`／`f16`；`f16` 是 `f13` 的 `repeat`——**上一版没修好，就补在这一幕**）。
  上面那两条判断门都发生在**动手之前**，盖不住"写出去之后"：
  ① 改完 `.js` → **先 `node --check` 再执行**（`f13`：模板字符串里一个反引号，四类命令当场全挂）；
  ② 改"**追加型**"文件（`CHANNEL`／`LOG`／账本／registry）→ **回读末两行**，确认旧内容还在
  （`f16`：把上一行整行当 `old_string` 替换掉了——**那不是追加，是覆盖**）。
  **故意只写动作、不写"要小心"**：两条各对应一个机器可判的现象（能否解析 / 旧行是否存在）。
  **也故意只加这一条**——§2 说过"一直往浅层堆东西会倒退"，§6 已经够厚了。

## 7. 反馈与选择压力

- **两条信号通路，互不替代**：
  - **`skips`**：某个 skill **该被想起来却没想起来**的计数（负向、稀有、直接指向"入口写坏了"）。
  - **摩擦力账本**（`.evolution/friction.jsonl`，append-only）：**碰壁的原始观察**——
    事实 + 那一眼。它记的是**过程**，不是结论，所以宁可粗糙也要写下来。
- **只记 `skips`，不记 `hits` 作为指标**：`skips` 是"该想起来却没想起来"的计数——
  这是唯一有信息量的负向信号（对应"缺页异常"）；`hits` 是自评，没有约束力。
- **phase 2（UI 插件，后续）**：加 host 钩子**自动统计** `skill` 调用（hits），自报降为只补「miss/问题」。
- **淘汰三触发**（三选一即可进入 retire 提议）：长期 0 hit / 被其他 skill 取代 / 明确过时。

## 8. 两条承重规则（理由优先：理由才可被重新演绎）

### 8.1 提案必须钉在它所提议的那个状态上（哈希绑定）

**做法**：`propose` 时记下目标 registry 条目 + `SKILL.md` 的 sha256；`accept` 前重算，
不一致即 `stale`，**拒绝收编**；`lint` 也会把它报成漂移。

**理由（推导，不是规范）**：里面执行的人每轮都会被换掉，什么判断都带不走——
**这台电脑是唯一的记忆**。因此"一个提案"与"它所依据的那个状态"之间的关系，
本身就**是留存边界**。提案一旦与目标脱钩，人批准的就是一个**已经不存在**的 diff：
他以为自己在批 A，实际落到的是 B。

**所以**：这条不是卫生要求，是"机器是唯一记忆"的直接推论。凡提案必绑定；绑不上就不许批。

### 8.2 来源是声明的，不是推断的（`write` 是硬约束）

**做法**：registry 的 `write` 取值只有三个——
- `user`：**人写的**。agent **一律不得直接改**，只能 `propose`（用户本人可用 `--user` 旁路）。
- `agent`：agent 自己写的，可自行 refine。
- `user-gated`：待定（还在 `scaffold/` 里，尚未成为 live `SKILL.md`）。

**理由（推导，不是规范）**：同上——执行的人每轮被换掉，所以"**这一块是谁写的**"
是这台机器**唯一**能区分「人的东西」与「自己的东西」的方式。若把这件事交给推断，
人的作品会被静默改写，**而且没有任何人会记得它原本长什么样**——因为记得的那个人已经不在了。

**所以**：来源一旦不确定，就不许自动改。宁可多问一次，不可少留一块。

> 这两条与 §0 的三条根认识同源：**机器是唯一记忆 ⇒ 关系必须被钉住；人被换掉 ⇒ 来源必须被声明。**

## 9. registry 与 `skillctl`

**registry 是生命周期决策的唯一真源**；skill 的 `name`/`description`/`whenToUse` 永远以各自
`SKILL.md` 的 frontmatter 为准（harness 只从那里读目录）。两者由 `lint` 强制对齐，防止漂移。

**提案生命周期**：`propose`（立提案，钉哈希）→ 人审 → `accept`（校验未过期后收编、version+1）
或 `reject --why 理由`（**理由必须留下**——被否决的理由是最贵的负向知识，而成功记录满街都是）。
`stale` 随时可查"哪些提案已经不能批了"。
**提案文件是凭据**（`.evolution/proposals/<name>.md` 带目标哈希与理由），**registry 只留结论**。

**提案历史（`proposalsHistory`，只追加、永不删）**：`proposals[]` 只放**未结案**的（一个 name 一条，
供 `accept`/`reject`/`stale` 一眼判断）；**一结案就移入 `proposalsHistory[]`**，被覆盖的提案文件
同时归档到 `.evolution/proposals/archive/`。
理由（`f17`→`f21`，两次实证）：**"每个 name 只留一条记录 + 整体重写"会让 `propose` 这种"看起来只是新增"
的动作天然变成销毁动作**——而被否决的 `why` 没有回滚面：git 只保护"提交过的中间态"，偏偏被否决那一刻
最没人提交（`f21`：A 的 `why` 在 git 全历史里搜不到，只剩一份**手工抄的**归档副本）。
所以历史区**只允许追加**；`retireProposal` **刻意不做去重**——宁可有重复的冗余，不可有静默的丢失。

命令面与字段以 `scripts/skillctl.js --help` 为准；`lint` 必须挡住这些漂移：
① registry 有条目但磁盘无 SKILL.md；② 磁盘有 skill 但 registry 无条目；
③ name ≠ 目录名或非 kebab-case；④ `description` 为空或超长（>500）；
⑤ `lineage` 指向不存在的条目；⑥ `tier`/`status`/`enforces`/`write` 值越界，或 `scope: project` 被登记；
⑦ 条目顶层出现野字段；⑧ **未结提案已 stale**；⑨ **被否决的提案缺少 why**（活账本与 `proposalsHistory` 都校）；
⑩ **活账本里同一 name 出现多条**（判断会失准）；⑪ **归档件文件名里的 `<name>.<旧状态>` 与 frontmatter 不一致**
（`f17` 那份手工副本文件名写 `open`、内容却是被否决那版——归档这种东西没有校验器看着就会自己烂掉）。

**registry 一律经 `skillctl` 写入，不手改 YAML**（唯一例外：用户直接编辑，之后必须 `lint`）。
理由：唯一真源一旦有两个写入口，就不再是唯一。

**本机事实（`f9`，已第二次撞）**：`node -e` 在本机 PowerShell 里会被**吞掉反引号**（报
`SyntaxError: Invalid or unexpected token`）→ **一律写 `.js` 文件再 `node <文件>` 跑**，别内联。

**写"实测／核实"结论时的硬要求（`f15`，(2026-09-30 核对)）**：凡"实测／核实／已验证"这类断言，
**必须带 `(YYYY-MM-DD 核对)` ＋ 出处**（哪次实测、谁核对、怎么复核）。理由：`f15` 的根因不是"事实过期"，
而是**写的时候没标它什么时候为真**——一条没有时效的"实测"，会被下一个执行体当成**无条件事实**
（§5.C 那句"子会话里没有任何标记"就是这么变成假事实的：它当时测过，后来 harness 变了）。

## 10. 护栏与优先级

- **优先级**：用户权限 > registry schema > skill 内容。冲突时停下问用户。
- **防漂移**：本引擎自身、registry schema、任何 meta 层 skill、以及所有 `description` 的改动，
  **必须用户确认 + 升版本**，不得"顺手静默改"。
- **确认门**：所有诞生/迭代/合并/淘汰，一律 staging → 提议 → 用户 approve/edit/reject。**人永远是主编，agent 是起草人。**
- **自述 vs 自宪**：skill、registry、状态文件是**自述**（可改写自己的描述，快档）；harness 代码与约定是
  **自宪**（决定我是什么，慢档）。本引擎只在快档内自由演化；越到慢档，必须过人的确认门。
- **版本耦合**：受管 skill 与 registry 都盖 `conformsTo` 戳；读到旧戳提示可能需要一次 refine。
  **本正文不抄 schema 的具体版本号**（抄了就会过期）——当前版本看 `registry.yaml` 的首行戳与
  `skillctl lint` 的输出（(2026-09-30 核对)：`REGISTRY_SCHEMA` 与 `registry.conformsTo` 必须同值）。

## 11. 与 session-handoff 的分工（对偶红线）

| | session-handoff | skill-evolution |
|---|---|---|
| 尺度 | 工作区（一个房间） | 整台电脑（整个生命） |
| 存续什么 | 局域自我（这单的经验/记忆/唤醒） | 全局躯体（跨任务的肢体） |
| 产物 | `.handoff/` 状态文件 | 全局/meta skills + registry |
| 生命周期 | 快照式 save/load | 进化式 诞生→选择→淘汰 |
| 速度 | 每次会话 | 每次摩擦 |

**红线**：本引擎**不记「某项目到哪了」**（那是 `.handoff` 的事）；只记「这类事怎么做、这个能力该不该有」。
凡你觉得是「历史教训、不是可执行流程」的，留在经验资产，不进 skill。

## 12. 边界（不做什么）

- 不复读模型已知的知识（互补铁律）。
- 不承载任何具体技能内容（那是各 SKILL.md 的事）。
- 不维护项目状态（那是 session-handoff / `.handoff` 的事）。
- 不存长文教训（那是经验资产的事）。
- 不手工维护 skill 目录（harness 自动渲染）。
- 不自行晋升/淘汰（`skillctl report` 只报告）。
- 不在未确认前把提案变成活 skill（确认门）。
- **不绕过哈希绑定收编过期提案**（§8.1）。
- **不直接改 `write: user` 的条目**（§8.2）。
- **不为"一句话指令就能解决"的问题造检测装置**（§6 末条）。
- **不让元工作的设计过程留在主 agent 的上下文里**（§5.C）——读出、记账、放下。
