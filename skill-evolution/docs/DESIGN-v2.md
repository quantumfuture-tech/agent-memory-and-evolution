# skill-evolution v2 设计备忘

> **状态：设计，未实现。**  
> 本文件不描述当前代码。当前仓库交付的是 v13 引擎；v2 没有分支、没有 flag、没有兼容层。
> 写这份备忘的目的，是让下一个接手的人知道为什么不能靠继续加子命令解决，以及哪些结构问题还没有定。

读者：准备改引擎的人。先读 `../SKILL.md` 的承重规则和 `../scripts/skillctl.js` 的现有实现，再读这里。

## 1. 为什么重画

v13 能用，而且核心不变量是对的：提案钉哈希、来源声明、否决理由保留。问题不在这些规则，而在它们被塞进了一个不断长大的命令面和数据形状里。

### 1.1 命令面已经有 18 个子命令

当前 `--help` 的命令区：`init`、`list`、`show`、`add`、`set`、`promote`、`propose`、`stale`、`accept`、`reject`、`friction add`、`friction list`、`friction clear`、`lint`、`roundtrip`、`render`、`report`，加上 `friction` 这一层，共 18 个入口。

这不是“功能多”，而是同一个生命周期被拆成了互相知道的命令：

- `add` 建档、`set` 改字段、`promote` 改层、`propose/accept` 改版本，各自直接改 registry；
- `friction` 是独立子树，和提案、条目之间没有结构关系；
- `lint/report/render/roundtrip` 是四种“读并报告”，但共享的中间表示很少；
- 每个新需求最自然的实现方式，是再加一个动词。命令越多，判断“现在该用哪个”的成本越高。

18 本身不是罪证。罪证是：**动作之间没有稳定的族，状态变化没有统一的记录点。**

### 1.2 摩擦条目缺归属维度

`friction.jsonl` 的一条记录大致是：

```text
id, at, what, lesson, type, repeatOf, reviewedAt, reviewBatch
```

它能回答“发生了什么”和“事前该问哪一句”，但回答不了：

- 这是哪个 skill、哪个工作区、哪类任务上的摩擦？
- 它和哪条提案、哪次收编、哪个条目有关？
- 同一个 failure type 在项目 A 和项目 B 都出现，算一次还是两次？
- 评估者给出的分类结论，除了 `friction-reviewed.md` 的批次头，还留在哪里？

结果是：`repeat` 只能看活账本；跨归档的重复要人重新看；提案被否后再提，无法自动引用“上次为什么否”。摩擦是引擎的入口信号，却在数据模型里没有归属。

### 1.3 沿革散在四个地方

当前至少四份材料都在讲“发生过什么”：

1. 条目内的 `changelog`（version、at、by、what）；
2. `registry.proposalsHistory`（提案结案记录）；
3. `proposals/archive/` 里的提案文件（被覆盖前的原文）；
4. `friction-reviewed.md`（已评估摩擦）。

它们各自合理，合起来却没有一个统一的“沿革”查询：一次 `accept` 会同时改 changelog 和 proposalsHistory，但不会产生一条可被引用的统一事件；一次 `set` 只改 registry；一次 `reject` 只留下提案历史。想知道“这个 skill 为什么是现在这样”，需要人把四份材料按时间拼起来。

### 1.4 提案是凭据，收编却不应用正文

v13 的 `accept` 校验哈希、升版本、写 changelog，但不修改 `SKILL.md`。它把“提案”当成待批的 diff，实际动作却更像“给已经落盘的正文登记一个版本”。

这不是实现 bug，是模型没有把“提议”“应用”“登记”拆开。v2 必须决定：提案是候选内容、还是对已应用内容的追认？两种都能做，但不能混着。

## 2. 目标与非目标

**目标**

- 把命令面收成五个动作族，让“现在该做什么”由状态决定，不由记忆 18 个动词决定。
- 给摩擦和沿革一个带归属、可引用的条目形态，而不是散落的文件。
- 把运行时事实与治理判断分开：前者可以自动追加，后者必须经过人。
- 保留 v13 的四条承重不变量：哈希绑定、来源声明、否决理由、往返无损。

**非目标**

- 不做自动自我修改。判断仍然在人这边。
- 不做语义搜索或向量索引。先解决结构，不解决召回质量。
- 不引入第三方依赖。Node 内置能力优先。
- 不在 v2 里自动迁移用户数据；迁移必须是显式动作。

## 3. 五个动作族

v2 的命令面按“动作的性质”分组，而不是按对象分组。下面是工作名，不是最终 CLI 名称。

| 族 | 做什么 | 吸收 v13 的哪些入口 | 关键约束 |
|---|---|---|---|
| **记** | 追加一条运行时观察：摩擦、证据、失败、用户纠正 | `friction add` | 只追加；必须带归属和“那一眼”；不直接改治理状态 |
| **读** | 按 id/范围读条目、提案、沿革、待评估项 | `list`、`show`、`stale` | 只读；索引可重建；不产生写 |
| **提** | 基于当前状态生成候选：新条目、修订、合并、淘汰 | `propose`、部分 `add` | 必须钉哈希；候选内容与目标分离；不生效 |
| **批** | 人对候选做接受/否决；记录决定与理由 | `accept`、`reject` | 人 gate；否决理由不可丢；接受后产生一条沿革事件 |
| **扫** | 校验一致性、重建投影、报告候选 | `lint`、`roundtrip`、`render`、`report` | 只报告或重建投影；不替人做晋升/淘汰 |

两个直接改字段的入口（`set`、`promote`）不再作为独立族存在：

- 对受管内容的实质修改，走“提 → 批”；
- 纯运行信号（如 `lastUsedAt`、`skips`）由“记”写入运行时侧，再由“扫”投影到治理视图；
- bootstrap 只保留 `init`，它不属于五个族，只建立空世界。

这不是把 18 个命令换个名字。它要求底层先有“候选内容”和“决定事件”两种可区分的数据，否则换皮没有意义。

## 4. 数据模型方向

### 4.1 分类三维：cause × type × scope

v13 的 `type` 是一个自由字符串，既表示原因，又表示形状，还暗示范围。v2 把它拆成三个正交维度。下面是候选枚举，不是已定 schema。

**cause（为什么没看见/没做对）**

- `perception`：信号就在眼前，但没看见；
- `knowledge`：不知道本地事实或约束；
- `judgment`：看见了，判断形状错了；
- `execution`：知道该做什么，执行时漏了；
- `environment`：工具、沙箱、运行时本身的行为。

**type（失败长什么样）**

- `misjudge`：把猜测当确认；
- `omit`：漏掉一步或一个输入；
- `detour`：绕路，重复已排除的路径；
- `rework`：做完才发现方向错；
- `overreach`：越过权限或范围；
- `tooling`：工具/格式/环境导致的失败。

**scope（影响半径）**

- `attempt`：单次动作；
- `task`：一个任务内；
- `workspace`：一个工作区/项目；
- `world`：整台机器/全局技能；
- `meta`：引擎、schema、协议本身。

三维不是标签墙。它的用途是查询和晋升判断：`cause=judgment × scope=world` 更可能值得改技能；`cause=execution × scope=attempt` 往往只需要一条 checklist。分类是声明的，不由工具猜；但工具可以拒绝空维度。

### 4.2 沿革条目化

v2 把“发生过什么”收成一种条目，而不是四种文件各说一套。候选形状：

```yaml
- id: h-0007
  at: 2026-01-01T12:00:00+08:00
  actor: user            # user | agent | runtime
  action: accept         # birth | propose | accept | reject | revise | promote | retire
  target: example-skill
  proposal: p-0003
  before: <digest>
  after: <digest>
  reason: "为什么做这个决定"
  decision: accepted     # accepted | rejected | superseded
```

规则：

- 只追加，不原地改；需要撤销就追加一条反向事件。
- 每条事件有稳定 id，可被提案、摩擦、其他事件引用。
- `actor` 是声明的；`runtime` 只能写运行时侧，不能写治理侧。
- `reason` 对人类可读；哈希只证明“是哪一个状态”，不替代理由。
- 沿革的当前视图可以由事件重建；registry 是投影，不是唯一记录点。

“条目化”不等于“一个 Markdown 文件一条”。物理形态（单文件、目录、JSONL）是 N2，不是这里先定的。

### 4.3 运行时与治理分离

这是 v2 最重要的边界：

| | 运行时侧 | 治理侧 |
|---|---|---|
| 谁写 | agent、脚本、hook | 人批准后的动作 |
| 写什么 | 观察、调用、失败、耗时、候选信号 | 条目状态、版本、沿革决定 |
| 写入方式 | 追加，低仪式 | 有 gate，产生不可丢的决定记录 |
| 失败代价 | 丢一条观察 | 人的作品被静默改写 |
| 典型文件 | 事件日志、摩擦账本 | registry/条目、决定历史 |

分离后的流程：

1. 运行时不断“记”；
2. “扫”把重复/高频信号聚成候选；
3. “提”把候选变成钉住状态的提案；
4. 人“批”；
5. “批”产生治理侧的沿革事件，运行时侧只保留引用。

这样 `write: user` 不再只是一个 CLI 分支，而是“运行时侧没有权限写治理侧”的结构性结果。v13 的直接文件修改仍然可能，因为两侧没有物理分开；v2 要把这个边界落到目录和写入口上。

## 5. 索引的位置（倾向，未定）

倾向：**索引是投影，不是真源。** 沿革事件和条目内容是源，列表、catalog、报告、stale 视图都可以从源重建。这样可以：

- 删除/重建索引而不丢判断；
- 用 `scan --rebuild` 修复不一致；
- 让 `render` 回归“只读投影”的定位。

代价是：每次读可能要重建，或者要维护缓存失效。是否值得，取决于条目规模。这个问题没有定，见 N3。

## 6. 迁移不是自动的

v13 的数据至少包括：`registry.yaml`、`proposals/`、`proposals/archive/`、`friction.jsonl`、`friction-reviewed.md`、`catalog.md`。v2 不能假设这些文件可以无损映射到新模型，因为：

- v13 的提案历史是记录，不是事件；缺少稳定的跨对象 id；
- `friction` 没有 scope/归属，只能从文本和批次头里推；
- `changelog` 的 `what` 是自由文本，不能稳定拆成 action/target/reason；
- 多次 `set` 没有留痕，无法还原每次字段变化。

所以 v2 的迁移应是：**先双读，再显式导入，再切换写入**。导入器要保留原始文件为只读证据，不能“迁移成功后删掉旧数据”。迁移的粒度、回滚和幂等性见 N5。

## 7. 还没定的结构问题（N1–N8）

### N1. “自我”的家在哪里

治理数据放 `$DSH_HOME/skills/.evolution/`，项目技能放 `<project>/.dsh/skills/`。v13 明确拒绝把 `tier=project` 登记进全局 registry，于是项目技能没有治理位置。

v2 要回答：一个 registry 管一个世界，还是多个世界？世界的边界是机器、用户、工作区，还是运行时实例？迁移机器时哪些 id 跟着走？这和 session-handoff 的 `.handoff/` 边界必须明确区分：一个是工作区记忆，一个是跨任务治理，不能互相吞。

### N2. 条目形态

单文件 registry 的优点是原子、易 diff；缺点是并发写、单条读取、历史膨胀。目录式条目（一个条目一个文件/目录）的优缺点相反。

需要定：条目 id 与 name 的关系；重命名是否改 id；条目内是否内联沿革；如何原子更新；如何避免两个写者覆盖；YAML 子集是否继续。

### N3. 索引是投影还是真源

见 §5。需要定：哪些视图允许重建；重建失败时旧索引是否继续服务；缓存放在哪；`lint` 是校验源还是校验投影；索引损坏时如何不让它反过来改源。

### N4. 暂存区的位置

v13 的草稿在 `.evolution/scaffold/`，提案文件在 `.evolution/proposals/`，归档在 `proposals/archive/`。这套位置有一个好处：不会被 skill 扫描器当成 live skill。坏处是候选内容和目标内容隔得很远，移动靠人。

v2 要定：暂存区是按目标就近（`<skill>/.staging/`）还是集中在治理目录；提案内容是完整副本还是 diff；“应用”和“收编”是不是同一个原子动作；git 里如何看见候选。

### N5. 迁移方式

需要定：双读窗口多长；旧 `registry.yaml` 是否继续可写；导入器如何生成稳定 id；冲突（同名条目、重复提案）如何报告；失败能否回滚；旧文件保留多久；迁移后 `lint` 是否还能读旧格式。

### N6. 世界作用域

`scope` 现在表示 durable/as-needed/transient，和“世界”不是一回事；`tier` 又混合了 project/global/meta。v2 要把“影响半径”和“治理归属”分开：

- 一个条目属于哪个世界？
- 项目技能是否进全局沿革，还是只进项目世界？
- 跨世界引用（global skill 被 project 提案修改）如何授权？
- 多工作区并发时，谁的代表作数？

### N7. 沿革的粒度

一条沿革是“一次动作”还是“一个条目的当前摘要”？前者可重建，后者读取快。需要定：事件和快照是否都存；重复事件如何合并；否决理由挂在哪；归档和沿革是不是同一套 id；删除条目后沿革是否仍可查。

### N8. 运行时与治理的边界

需要定：哪些运行时信号自动写（调用、失败、耗时、用户纠正）；哪些必须人确认；hook 能否直接产生提案；`skips/hits` 由谁计数；运行时侧的写入失败是否阻塞主任务；冲突时谁优先。

边界不清，就会出现两种坏结果：运行时偷偷改了治理状态，或者所有观察都要人确认，最后没人记。

## 8. v2 的验收条件（建议）

在实现前先把这些写成测试，否则很容易做成“命令改名、数据更复杂”：

1. 从空目录 `init` 后，能完成一次“记 → 读 → 提 → 批 → 扫”的闭环。
2. 提案目标改动后，`批` 必须拒绝；拒绝理由进入可查询的沿革。
3. `write: user` 的治理写入在运行时侧没有入口，不靠调用方自觉。
4. 删掉所有索引/投影后，能从源重建出同样的列表、catalog 和 stale 视图。
5. v13 的 `registry.yaml` 能被只读导入，原始文件保留，重复导入幂等。
6. 旧的四条承重不变量各有对应测试；不是“v2 重新实现了一遍，应该没问题”。
7. 18 个入口收敛到五个动作族后，`--help` 不出现“这个命令该在什么时候用”的解释长文。

## 9. 建议的推进顺序

1. 先定 N1（世界边界）和 N4（暂存区），因为它们决定目录形状；目录定错，后面都要搬。
2. 再定 N2（条目形态）和 N7（沿革粒度），写一个只读原型验证查询。
3. 用 v13 的真实数据做一次离线导入演练，验证 N5；不要先写 CLI。
4. 最后才收敛命令面。五个动作族是结果，不是起点。
5. 每一步都保留 v13 的回归测试；v2 通过之前，v13 仍是唯一可交付版本。

- 本文件不是发布说明，不承诺日期。
- 当前 `skillctl.js` 没有 v2 开关；不要根据本文件推断已有 API。
- 若要开始实现，先在本文件下补一份“决定记录”，把 N1–N8 逐项标成已定/未定，再动代码。
